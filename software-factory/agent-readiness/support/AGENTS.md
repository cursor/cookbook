# AGENTS.md

Rules for agents that change the Agent Readiness accelerator. To run an audit on a repository instead, follow [skill/agent-readiness/SKILL.md](../skill/agent-readiness/SKILL.md). This `support/` folder holds maintainer tooling. The copyable skill lives at `../skill/agent-readiness/`; unit tests and sample reports stay at the example root.

## Secrets and identifiers

- Do not commit credentials, tokens, `.env` files or local override files.
- Do not commit customer names, tenant ids or real email addresses. Fixtures use placeholder contributors (`Contributor A <a@example.com>`).

## Shape of the code

- TypeScript only, run by Node 22.14 or later with type stripping. Use only erasable syntax: no enums, namespaces or parameter properties, and `import type` for types.
- `../skill/agent-readiness/` is what customers copy. It has no runtime dependencies. `@cursor/sdk` is a dev dependency of `evals/` only.
- Scripts own evidence, scoring and sealing. A model never decides that a check passed, picks planted faults, or writes a level. Only `readiness run` and `readiness replay` create executed or clean-replay evidence.
- `scripts/lib/levels.ts` is the only place level rules live, and it reads its thresholds from the rubric. Renderers read everything, including component names, from `report.json`.
- `gh` is called only from `scripts/lib/gh.ts`. Container runtimes are called only from `scripts/lib/container.ts`.
- After changing anything under `skill/agent-readiness/scripts`, `rubric`, `schema` or `templates`, run `npm run release-manifest` so `RELEASE.json` matches. A test fails until you do.
- Fixtures store dotfiles and agent files under fixture names (`dot_cursor/`, `dot_nvmrc`, `AGENTS.fixture.md`, `SKILL.fixture.md`), so their deliberately wrong instructions never steer an agent working in this repo. `tools/fixture.ts` (here under `support/tools/`) restores the real names in a temp copy.
- `../examples/sample-report.md`, `sample-report.html` and `sample-report.json`, and their `-first` versions, are generated by `npm run sample`. Never edit them by hand.
- Every environment variable the accelerator defines starts with `SA_`, in the scripts, evals, tools, tests, workflows and docs, for example `SA_READINESS_IMAGE`. Names other systems define (the OS, CI, Cursor, package managers, a repo's registry tokens) keep theirs. `tests/env-prefix.test.ts` fails on any other name; add a genuinely external one to `EXTERNAL` in `support/tools/env-prefix.ts`.

## Adding or changing a check, level rule or scenario

1. Add a fixture under `support/fixtures/` that fails the new check, with an `expected.json`. The `healthy-node` fixture must still pass.
2. Write the change into a new rubric file, `rubric/<next-version>.json`. Never edit a released rubric; old audits are never rescored.
3. Add at least one skill eval case under `support/evals/cases/` that would have failed before the change.
4. Rerun the full eval set and commit the new `support/evals/baseline.json`.
5. Never change an `expected.json` to make a run pass without a written reason in the PR description.

## Changing SKILL.md, the references or the report wording

These change what the agent does or what the reader sees, so they follow the hill-climb rule in [evals/METHOD.md](evals/METHOD.md): one failure mode and one lever per change, a case or test that would have failed before it, and before/after numbers on the same cases recorded in the PR description. Keep a change only if its target improves and no hard gate drops.

## Field findings

A customer's `readiness feedback` bundle (`.agent-readiness/feedback/*.json`) holds the rubric version, check, evidence digest and a note, and no source code. To act on one:

1. Reproduce it as a fixture that shows the finding.
2. Decide whether the check is wrong (fix the rule, following the steps above) or the docs are wrong (fix `references/checks.md`).
3. Link the bundle's id in the PR description.

## Citations

Every number or external claim in the shipped docs links its source and states its caveat. The verified list lives in `references/checks.md`.

## Before committing

Run `npm run check` from the example root (`software-factory/agent-readiness/`). Run `npm run evals -- --tag smoke` when you change `skill/`, the rubric or `support/evals/`.
